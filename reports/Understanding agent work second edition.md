# Evidence narrows what the product can claim

The evidence as of 16 November 2026 supports a narrower product than the first edition described, and it supports it less firmly. The product the evidence can defend is an optional local tool that works beside several coding agents. It computes a module-level picture of each agent change from git and the import graph, with no language model in the facts. On a small number of selected changes it asks the developer to mark on that picture what they expect, before they read the agent's plan. It then shows the computed outcome beside the mark, shows the dependency path to each part the developer missed, and asks the developer to find the cause. It keeps a private record of predictions against computed outcomes, including operational facts such as dropped tables and resources to be destroyed. Three things changed since the first edition. First, the gap is much narrower: quizzes before the code is written, prediction exercises and records across sessions all exist already, and only two parts were not found anywhere (a prediction made by marking a diagram, and an outcome diagram computed without a model). Second, every near-test of the core act found no learning gain: Lead-and-Reveal in two studies, the Vibe-GUIDE system graph, and choose-first-then-see in Gajos and Mamykina. Third, a body of research on supervising automation, which the first edition missed, says that prediction alone is the weakest form of anticipation training and that people learn when they must reach the conclusion themselves from evidence. The evidence conflicts with the owner's constraints in two places: it leans against the idea that system-level skill can be held without code-reading fluency, and it does not support the claim that months of practice build a skill that carries to other systems. Nobody has tested prediction before an agent's change with working engineers. The product would have to produce that evidence itself, and it should be built to do so.

## How to read the labels

Every finding carries five labels. **Type** is one of: controlled study (a meta-analysis of controlled studies is marked as such), observational data, survey (interview studies are marked), incident, opinion. Tool facts add official documentation and repository read. Section F adds one more type, measurement, for numbers produced by scripts on a real machine during this research. **Sells AI** says whether the source sells AI coding tools, or tools that review or measure AI code. Academic sources in sections C and D do not sell AI tools unless a row says otherwise. **Strength** is how far the finding can be relied on for this question: strong, moderate or weak. **Read** says how the source was read. "Full text" means the document was downloaded and the passage was read in it. "Abstract only" means only the abstract or record was read. "Secondary" means the figure came from another paper's description, a search summary or press coverage, and is unverified. "Page" means a public web page was read, either a vendor page whose full report is gated, or a page read through a tool that returns an extract. Each section keeps measured findings in tables and puts claims and inference in the prose after them.

### What the measurements show, and what they do not

Handing code generation to AI lowers immediate comprehension of the result. Two randomised experiments agree in direction and in size (d = 0.738 and d = 0.9). The claim holds for small, new, self-contained tasks tested minutes later. It has three limits that the first edition did not state. The loss in the agent experiment was a loss of recall, and the reasoning score was not significantly lower. The loss did not produce a significantly worse result on the follow-up task. And a preregistered experiment with 151 mostly professional participants found that AI-assisted code was no harder for others to change. If not understanding has a cost, the evidence places it in system-level complexity over months and in operations, not in the readability of single changes. This last sentence is an inference.

The column for "Code" is empty in every incident row. In each case the person could have read every line the agent wrote and still been surprised. The agent misreporting its own work is common in two independent data sets: 22.58% of misalignment episodes, and a self-report that covers about one action in eleven. An agent's summary is not a reliable account of what it did.

Experienced users grant more blanket permission and also interrupt more. That is consistent with supervising by exception. It moves human judgment from "before each action" to "during and after". Review became thinner across open source whether or not a repository used agents, so "agents caused shallow review" is not supported by the one study with a control group.

"Cognitive debt" and "comprehension debt" remain terms, not measured quantities. Storey's paper is a conceptual essay with one classroom anecdote. It proposes measures as suggestions only and warns against using AI to write the explanations: "This substitutes the appearance of understanding for the real thing" ([Storey, arXiv 2603.22106](https://arxiv.org/pdf/2603.22106); opinion; sells AI: no; weak as evidence; full text).

### Unknown

No study measures whether experienced engineers understand agent-made changes to systems they own. The nearest are ten people on unfamiliar code and a 12-person tool probe. No telemetry shows whether agent diffs are opened or read. No study measures skill in working engineers over time; "skill atrophy" in professionals is a hypothesis. No study measures a person's or team's understanding and then a later cost. No verified case exists of a quiet failure, such as a security hole or drift found months later, traced to someone not understanding an agent's change. No study measures revert rates of agent pull requests.

The first edition ranked "reach of a change" seventh with P "weak to moderate". Round 2 found direct evidence, some of it thirty years old, that experienced developers predict the reach of a change with high precision and lower recall, do not know how accurate they are, and do not improve with years. That is the profile for which recorded predictions with feedback are usually prescribed. It also says what the most useful output is: the list of what the developer did not predict. Both statements are inferences.

The central weakness has not moved. Almost every source shows that a problem exists. Almost none shows that a named skill, once trained, reduces it. The claim in the first edition that METR "found no measured difference in speed-up by developer or task type" is not in the cited post and is withdrawn.

### What the evidence says about "nothing at the level of code lines"

The first edition called this an open dispute. Round 2 read the sources, and the evidence leans against the claim that system-level skill can be held without code-level fluency. It is indirect. Expert engineers rank attention to coding details first of 54 attributes. Architects who code make fewer errors in architectural code. Non-developers building with agents are the only group that reports giving up because they cannot understand the output. The capacity to check agent work tracks how much a person still codes without AI. The strongest evidence on the other side is the manager study, and even there managers who write no code are expected to read and judge it.

Two points support the constraint as a scope for the product. The "Code" column is empty in every incident. And the one well-powered experiment at code level found no maintainability penalty. So the constraint is defensible as a statement of where the product works. It is not defensible as a claim about what engineers need. No study tests whether someone with strong system skill and no code fluency can supervise agent work to a good outcome. The honest position for the product is: it works above the level of lines, it does not replace reading code, and its users are assumed to be able to read code. A product that told engineers they no longer need that ability would go against the evidence.

### Unknown

Whether any of these skills, measured in a person, predicts fewer defects or incidents with agents. Whether any can be trained by a tool. What predicts good incident response or good supervision of agents in an individual. No study with measured outcome differences between senior and junior engineers working with agents was found.

### What carries over to developers

The direction of the trade-off carries. A coding agent selects and carries out the action, so the developer sits on the costly side of the boundary Onnasch and colleagues found. The mechanism carries: passive processing replaces active choice. Bainbridge's 1983 argument carries: an operator's working knowledge consists of "results of making predictions and decisions about the process", and it "develops only through use and feedback" ([Bainbridge 1983](https://doi.org/10.1016/0005-1098(83)90046-8); opinion and review; full text). The ranking of what decays carries: cognitive, accuracy-based, recall-dependent skills go first, and predicting what a change will do is all three. These are inferences from other fields.

The size does not carry. The laboratory failures are sudden and must be handled in seconds. A developer usually has minutes or hours and can revert. Clinical figures such as "26% more errors" should not be quoted for software. Complacency was strongest when automation was almost never wrong and the operator was busy with other tasks. Coding agents are wrong often enough that developers see failures. Against that, more than 10% of Codex users manage three or more concurrent agents at some point each week ([OpenAI Codex paper, arXiv 2606.26959](https://arxiv.org/abs/2606.26959); observational data; sells AI: yes; abstract only), which is the multitasking condition.

A prediction before the agent acts is the cheapest form of "doing part of the task by hand" available to a developer who does not write the code. The two studies that support this (Parasuraman 1996, Kessel and Wickens 1982) had the operator do the whole task, not forecast it. The match is imperfect, and both were read at abstract level only.

The drawn picture of what happened is a transparency display. The evidence says such displays help, do not fix over-reliance on a usually-right system, lose value under time pressure, and help high-capacity users most. The picture alone should not be expected to keep understanding intact.

The human-factors framing has reached software as position papers and interviews. A November 2026 preprint recommends "pre-commitment mechanisms [that] have the user record their own view or decision before seeing the agent's recommendation". It reports no experiment ([Mitchell, Ghosh, Passi 2026](https://arxiv.org/abs/2608.23642); opinion; sells AI: not checked; full text). Interviews with 17 experienced developers found that they monitor agent reasoning "perfunctorily" and use "test results as guarantees for code correctness"; twelve of the 17 worked at the authors' own company ([Dhanorkar et al. 2026](https://arxiv.org/abs/2606.05391); survey by interview; weak to moderate; full text).

### Unknown

No controlled study in aviation, process control or driving asks operators to predict the automation's next action as a standing practice and compares them with a control group on later understanding. No controlled experiment measures situation awareness or mental-model accuracy in developers who supervise coding agents. No study follows operators for months after any of these interventions. No study tested how long the benefit of a manual interval lasts beyond the same session.

### What this means, read plainly

**Prediction before the outcome.** The pretesting effect is real in students and attaches to what was guessed. It needs something to generate from: the generation effect is 0.05 for unfamiliar material, and problem solving first fails when the learner cannot tell what in the attempt was wrong. So a prediction about a part of the system the engineer does not know may give little memory benefit. The first edition treated prediction as the supported core. The second round weakens that. Every near-test found no learning gain, prediction-only training was the weakest arm in the driving study, and awareness probes did not transfer. Section J sets these out together.

**Feedback.** This is where the evidence is strongest and where it changed most. A bare right-or-wrong signal sits near 0.24 to 0.46 in students. Feedback that explains why sits near 0.99. A diagram that only shows what happened is corrective feedback. A diagram that shows why the missed part was reached, by its dependency path, is closer to the high-information form. The first edition asked whether a delay of minutes between prediction and result matters. The answer on current evidence is no (g = 0.03). Timing is not the thing to optimise. Content is.

**Calibration.** Training with feedback reliably makes people less confident. That corrects overconfidence. It is not the same as better judgment. Forecasters held the gain for a year while feedback continued. Analysts became more underconfident where they were already underconfident. Oncologists did not improve. More years of experience did not calibrate forecasters or maintainers. No study shows that calibration persists after feedback stops. No human experiment shows that one scoring rule teaches better than another. The supportable design is to show an engineer their own calibration curve, not to push confidence down.

**Transfer.** Near transfer is supported: the next change to the same system. Far transfer is not: a new system, or "systems thinking" in general. The one software finding, the cognitive-training meta-analyses, the domain-general reversal in productive failure, the g = 0.04 general effect of prequestions and the human-factors transfer results all point the same way. What might carry across systems is a habit and a method, by analogy with forecasting training. That is an analogy, not a finding.

**Experts.** Assistance harms the knowledgeable less than it helps novices, and the authors of the meta-analysis advise giving it when unsure. For engineers who know some parts of a system and not others, optional explanation that can be collapsed fits the evidence better than no explanation. Experts improve without noticing it (Horswill), so self-report will under-detect gains.

**Diagrams.** No controlled evaluation of the C4 notation was found. No controlled evaluation of a diagram of a change was found other than Vibe-GUIDE, which was close to null on its main measure. The positive results are for whole-system views used for exploration, and for accurate human-made design documentation. The owner's constraint that diagrams are drawn for the developer is compatible with the evidence: learner drawing does not reliably beat a good provided picture ([Fiorella and Zhang 2018](https://ifp.nyu.edu/2018/journal-article-abstracts/s10648-018-9444-8/); systematic review; students; abstract only). The evidence that most affects the design is about wrong artefacts. Developers spot an incorrect machine-made artefact about half the time and stay confident. Since the outcome diagram is the feedback the prediction is scored against, a wrong diagram teaches the wrong lesson. No study measures the harm from an inaccurate diagram specifically.

**How often to ask.** No evidence gives a safe frequency. The one programme that changed professional behaviour sent zero to two items a week. In the Cochrane review, repeating feedback more often went with smaller effects. Weekly reminders did not sustain use over 16 months. Probe and training effects in the human-factors studies decayed within a week, which implies the practice must continue at some rate. Skill half-lives of about 6.5 months come from skills left wholly unused, which suggests decay is a matter of months, not days. None of this was measured in software. Any rate the product picks is a guess to be tested.

**Voluntary use.** No study was found, in any profession, of what keeps people using an optional, effortful learning tool for months. Streak displays help while intact and demotivate once broken (secondary). Maintainers who state high confidence "were interpreted by other software professionals as more knowledgeable ... even in situations were the low confidence predictions were clearly more accurate" (Jørgensen and Sjøberg, preliminary; full text). That works against honest confidence ratings if they are visible to colleagues.

### Unknown

Whether predicting change impact, with feedback, improves engineers' understanding or judgment at all. Whether any gain accumulates over months, and how fast it decays. Whether calibration on change predictions improves decisions, such as what to review closely. Whether a per-change diagram helps comprehension. Whether explaining a prediction to a colleague adds anything, in professionals.

|---|---|---|---|
| Which files or modules will change | `git diff --name-status`, mapped to modules | Repository only | None for files. Module mapping depends on the grouping. |
| Whether a new dependency between modules, or a cycle, appears | Import-graph difference before and after | Repository only | Dynamic imports, dependency injection, reflection. No measured miss rate was found. |
| Which other modules could be affected | Direct importers of what changed | Repository only | Overstates real impact. Also misses where edges are missed. |
| Whether a third-party dependency is added | Manifest and lockfile difference | Repository only | Close to exact |
| Whether a public interface breaks clients | [oasdiff](https://github.com/oasdiff/oasdiff) or [buf breaking](https://buf.build/docs/breaking/) | A schema file that matches the code | None where the schema exists |
| Whether a migration drops a schema, table or column | [Atlas](https://atlasgo.io/lint/analyzers) DS101 to DS103 ("loss of data", exit code 1) or [squawk](https://squawkhq.com/docs/rules) `ban-drop-*` rules | Migration SQL. squawk needs no database. | A rename appears as a drop plus an add in Alembic autogenerate |
| Whether a migration could fail on existing rows, or breaks old readers | Atlas MF and BC codes; squawk `adding-not-nullable-field`, rename rules | Migration SQL | The answer is "might", not "will" |
| Whether a down migration exists | Alembic: a non-empty `downgrade()`. Django: no operation with `reverse_sql=None`. Flyway: a matching undo script. | Repository only | Existence is not reversibility |
| How many resources a plan creates, updates, replaces, destroys | Count of `resource_changes` by `actions` in [`terraform show -json`](https://developer.hashicorp.com/terraform/internals/json-format); `change_summary` with `add`, `change`, `remove` in [`terraform plan -json`](https://developer.hashicorp.com/terraform/internals/machine-readable-ui) | A saved plan file, which needs credentials and state | A replacement adds one to both `add` and `remove` in the summary |
| Whether a named resource is replaced, and why | Its `actions` pair, `action_reason`, `replace_paths` | Same | None documented |
| Whether a change touches live infrastructure at all, or widens permissions | Exit code of [`cdk diff --fail`](https://docs.aws.amazon.com/cdk/v2/guide/ref-cli-cmd-diff.html), [`kubectl diff`](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_diff/), `pulumi preview --expect-no-changes`; `cdk diff --security-only` | Cloud or cluster access | Text output only for anything finer |
| "This is a contained change" | No single fact | A model, or a rewording as a closed choice | Not measurable |

All rows are official documentation, read in part, strong for what the documents state. The Atlas pages mark some analyzer groups as paid. The JSON shape of `pulumi preview --json` was not found and is unverified.

The operational level was "not researched" in the first edition. It is now documented, and it is the level of the incidents. Three limits apply. All infrastructure checks need a plan produced with credentials and live state. A tool with only git can read a plan file or a CI log that someone else produced, and cannot run the plan. Second, every check needs the files to exist. None computes a fact for a change the agent has only planned. Third, "a down migration exists" is checkable and "the change is reversible" is not. Django's own documentation says an operation is reversible "apart from any data loss, which is irreversible". The Grigorev incident would have been visible in a count of resources to be destroyed. The PocketOS deletion was one API call with a token found in a file, and none of these checks would have seen it. Both statements are inferences.

Function-level facts are weaker than module-level ones. The best measured Python call-graph tool has precision about 99.2% and recall about 69.9%, on five packages of under 3.5k lines each with hand-built ground truth, so the recall figure should not be read as a rate for large codebases ([PyCG, arXiv 2103.00587](https://arxiv.org/pdf/2103.00587); controlled evaluation; sells AI: no; moderate; full text). In impact prediction on 17,000 mutants in 10 Java projects, the most basic call graph gave the best F-score in 18 of 50 cases, a modest margin ([Musco et al., arXiv 1812.06286](https://arxiv.org/pdf/1812.06286); controlled evaluation; no; moderate; full text). The main build-free library for precise name resolution, stack-graphs, was archived in September 2025 ([github/stack-graphs](https://github.com/github/stack-graphs); repository read; page).

A language model alone is not reliable for drawing the system. On 17 Java microservice systems, GPT-4o reached a mean F1 of 0.604 and the other model tested reached 0.254. Both left relationships out more than they invented them. Both models are old by November 2026 ([Liljas et al., ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.62); controlled evaluation; no; moderate; full text). Across 340 repositories and 4,137 generated views, "all the models performed poorly on completeness (>82% failures)" in zero-shot use, working "at the code level rather than architectural abstractions" ([Sathvika et al., arXiv 2603.21178](https://arxiv.org/pdf/2603.21178); controlled evaluation, preprint; no; moderate; full text). The division of work that follows is an inference: nodes and edges come only from computed facts, and a model may group, name and describe them.

Of twelve further tools read, none produces a before-and-after module-graph difference out of the box. import-linter (Python) and Nx (its own workspaces) come closest to a ready graph. ast-grep extracts import statements in many languages without a build and leaves resolution to the caller. For drawing, ELK, through elkjs or D2's bundled Go port, is a free engine that handles nested boxes ([ELK](https://eclipse.dev/elk/); [D2](https://github.com/terrastruct/d2/blob/master/README.md); official documentation; part).

### What is not possible today, on this evidence

A third-party tool cannot read the agent's complete intended change before any edit, in a documented way, except in Claude Code and, through a wrapper, in Codex. It cannot ask anyone in cloud or unattended runs. It cannot enforce anything through command hooks that fail open. It cannot get a complete call graph for Python or JavaScript without running the code. It cannot compute operational facts without a plan artefact or a migration file. It cannot see what an agent does through an API call that leaves no file.

### Unknown

The miss rate of import graphs on real repositories. Timings and change sizes outside three Python repositories and one TypeScript repository. Whether the plan text is on screen before the plan hook fires. How each agent behaves while a hook waits minutes for a person, beyond the Claude Code example. How well a module-level difference matches what expert reviewers judge to be the real effect of a change.

The owner asked for ambition. The evidence supports ambition in three places. A tool that records a prediction, a computed outcome and a later result for the same person is the instrument that every section of this report lacks. A position paper recommends pre-commitment for agent oversight and reports no experiment. An open-source project can run the experiment and publish it. The author of Learning Opportunities has published work on developer learning and includes a measurement playbook; the notes name her as a likely reviewer.

## I. Design implications the evidence does not support, and where it conflicts with the owner's constraints

**"The product builds skills over time."** The evidence supports a narrower claim: it can build and keep knowledge of this system, and it can keep calibration in check while feedback continues. It does not support a general skill that carries to other systems. Far transfer is near zero in controlled studies. Maintenance experience did not carry across applications. No study measures accumulation over months or decay after the practice stops. This conflicts with the constraint as the owner states it, unless "skills" is read as knowledge of one's own systems and honest confidence about changes to them.

**"Nothing at the level of code lines."** As a scope, this fits where the incidents are. As a claim about engineers, the evidence leans against it. The product should not say or imply that code reading has stopped mattering. No direct test exists either way.

**"The core act is prediction."** The evidence does not support prediction as the act that produces learning. It supports reaching a conclusion oneself from evidence, and feedback that explains why. Prediction is a reasonable way to start that process and a good way to measure it. On current evidence the computed picture and the explanation of misses have more support than the guess. The owner should treat prediction as the measuring step and the starting point, not as the proven mechanism.

**"Diagrams are drawn for them."** The evidence is compatible with drawing for the developer. It does not support the claim that a diagram of a change improves comprehension. The only controlled test was near null on its main measure, with a hint that relationship understanding improves and exact-location knowledge falls. No evidence supports the C4 notation.

The evidence also does not support: asking on every change; any quiz that blocks a commit or merge; a diagram drawn by a model alone; scoring free-text predictions, or predictions about who is affected, as if they resolved cleanly; whole-system maps as the main view; reminders or streaks as the way to keep people using it; pushing confidence down across the board; a fixed prediction form asked the same way each time; any claim that the product reduces incidents, prevents skill loss or improves engineering outcomes. Skill loss in working engineers has not itself been measured. An improvement in prediction accuracy inside the tool should not be assumed to produce better engineering.

## J. The near-tests that found no gain, and what they imply

Four results come close to testing the core act. None found the gain the product hopes for.

**Lead-and-Reveal, two studies.** Learners explained each step before the AI's code was revealed. Study 1 (82 undergraduates): b = 26.8, p = .058, not significant, underpowered by the authors' own calculation. Study 2 (42 participants): no difference between techniques (p = .150), and Lead-and-Reveal scored M = 55.0 against M = 57.6 for baseline. The one positive finding is a correlation between perceived and actual ability of r = .26 against r = .16 for baseline, not tested against each other. The cost was 1.82 times the baseline time. Population: novices, line level, a chat tool.

**Vibe-GUIDE.** A system-level module graph against chat only, 16 developers. Primary comprehension δ = +0.03 with interval [-0.49, +0.53]. Trust was lower with the graph. Later tasks slowed less. The graph was made by a model, the test was scored by a model, and there was no prediction step.

**Choose first, then see.** In Gajos and Mamykina, 268 people made their own choice and then saw the AI's recommendation and explanation. They decided better and showed "no learning". People who got the explanation without the recommendation, and had to reach the decision themselves, learned. Population: strangers on a one-off nutrition task.

Three further results point the same way. Awareness probes changed behaviour in the moment and did not transfer. Prediction exercises alone were the weakest arm of hazard-perception training. A feedback module did not improve prediction in 148 oncologists.

Each of these differs from the product. The first is novices at line level. The second has no prediction and a model-made picture. The third has no prior knowledge and no stake. A developer predicting on their own system has both. Those differences are reasons the results might not carry. They are not evidence that the product works. The plain implications are these.

First, the default expectation is no measurable learning gain from "state your guess, then see the answer". The product must be designed and described on that basis until its own data says otherwise.

Second, the results agree on what separates the conditions that taught from those that did not. People learned when they had to work from evidence to a conclusion, and when feedback explained why. They did not learn when an answer was handed over after a guess. So the step after the reveal is the one to design most carefully.

Third, the effort has a cost that users feel. Lead-and-Reveal took nearly twice as long. Forcing designs and graphs lowered trust and liking. The Socratic assistant was routed around.

Fourth, small studies cannot settle this. Lead-and-Reveal had 82 participants and needed 153. Vibe-GUIDE had 8 per group. A product study with a dozen users will produce the same ambiguity.

Fifth, the one consistent positive signal is about relationships and later work: relationship questions leaned toward the graph, later tasks slowed less, and the projection probes were the only ones whose effect persisted. If the product has an effect, the evidence suggests looking for it in understanding of how parts connect and in later changes to the same system, not in recall of what a change contained.

## K. Open questions the product itself would have to measure

Does recall on reach predictions (the share of touched modules the developer named) rise over months on a given system? Does it rise for areas the developer has not predicted before? Does it carry to a second system? Does the gap between stated confidence and scored accuracy narrow, and does discrimination between safe and risky changes improve, or does confidence only fall? Do developers who predict understand the next change better than those who only see the computed picture? Does finding the cause of a miss add anything over seeing the path? What rate of asking do people still accept after three and six months, and at what rate does accuracy decay when they stop? Do people hand the prediction to an AI? Does the computed picture agree with what expert reviewers judge to be the real effect of a change, and how often does a missed edge mislead? Is the plan already on screen when the plan hook fires? Do operational predictions (destroyed resources, dropped columns) behave like structural ones? Does any of this relate to later outcomes: rework, review time, defects, incidents? Do developers who run several agents at once use it at all? Each question is answerable only with the product's own data. None is answered in the literature found.

What is unknown, stated once: whether this kind of practice works for experienced engineers, whether it lasts, whether it transfers, how often to ask, whether people will keep using it, and whether understanding more leads to measurably better outcomes.

## L. Risks

**The method does not work.** There is no direct evidence that it does. Every near-test found no learning gain. This is the most likely failure, and the product's own measurement is the only way to find out.

**Training on a wrong picture.** The outcome picture is the feedback. Import graphs miss dynamic links at an unmeasured rate. Developers do not catch wrong machine-made artefacts and stay confident. A developer whose correct prediction is marked wrong learns the wrong thing. This is the largest risk the evidence points to, and it is why the picture must be computed and must say what it cannot see.

**Training on a proxy.** Structural reach is not real consequence. Awareness correlates with performance at r = 0.26. Confidence built on structural feedback could be misplaced on questions of behaviour and downstream effect.

**Low voluntary use.** Students knew they understood less with an agent and still preferred it. Tools that test have few stars. No study shows what keeps professionals using an optional, effortful tool for months. Engineers whose work is moving toward verification may see a prediction prompt as one more supervisory task.

**Users dislike what helps them.** In three studies, the people who benefited from forced engagement trusted or liked it less. Feedback from users will under-rate the product and may steer the design toward what works less.

**It helps those who need it least.** Forcing designs helped people high in need for cognition. Transparency helped people with high attention control. The product should expect to help already-engaged developers most.

**Narrow learning.** People become wary of the kind of error they have seen and stay complacent about other kinds. A developer may get better at predicting import reach and no better at anything else.

**Calibration that only lowers confidence.** Training made analysts more underconfident where they were already underconfident.

**Tuning out.** Repeated prompts are dismissed at high rates in clinical systems. Nothing is known about learning prompts in developer tools over months.

**Attention on the self, and social pressure.** A record of the engineer's accuracy sits where feedback more often harms. If colleagues can see confidence ratings, the reward for sounding sure works against honesty.

**Limited reach of the prediction moment.** The full intended change is readable before edits only in Claude Code and, through a wrapper, in Codex. The developer may already have seen the plan. Cloud and unattended runs have nobody to ask. Changes made through shell commands or API calls can bypass the hooks.

**Dependence on vendor interfaces.** Hook payloads carry no stability promise. Headless Claude Code runs are set to skip hooks by default. Products were renamed or replaced twice in 2026 in the documentation read.

**The operational level stays out of reach.** Infrastructure facts need credentials the tool does not have. The worst incident on record was one API call that no file-based check would have seen.

**Absorption by existing tools.** visual-explainer, Rasoi or a vendor's plan review could add a marking step. For a free open-source product this is a risk to adoption, not to the aim. If the idea spreads, the aim is served.

**Scale.** The measurements cover three Python repositories of up to 2,943 modules and one TypeScript repository. One real commit had 822 direct dependents. Agent changes are reported to be larger than human ones.

**The evidence base is dated and partial.** METR calls its own 2025 result out of date. The studies of model-drawn architecture used older models. Much telemetry comes from vendors that sell review or analytics products. Most human-factors sources were read at abstract level. Most 2026 software sources are preprints. The absence of a matching tool is "not found", and a vendor roadmap was not checked.
