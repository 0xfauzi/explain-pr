EXAMPLE: Why a retried charge needs a key

Without the key, a slow payment gateway makes the worker charge the customer twice. This page shows where and why. Nothing you click here changes any code.

The worker sends a charge, the gateway takes 1.2 s to reply, and the worker's timeout is 0.8 s. With no idempotency key, what does the customer see?

  1. One charge, because the gateway rejects the second request
  2. No charge, because the timeout cancelled the first request
  3. Two charges, because the retry looks like a new request

A client timeout stops the client waiting. It does not stop the gateway, which finishes the first charge anyway.

The gateway cannot tell a retry from a new purchase, so it charges again (worker/charge.py:41).

With the key turned on, how slow must the gateway be before the customer is charged twice?

  1. Slower than the timeout, 0.8 s
  2. No latency causes a double charge
  3. Slower than two timeouts, 1.6 s

In one or two sentences: why does the key make the retry safe, and what must the worker do with the key across a restart?

The gateway stores each key and returns the first result for any repeat, so a retry cannot create a second charge. The worker must store the key before the first send and reuse it after a restart, or a restarted worker invents a new key and the protection is gone (worker/charge.py:30-36).

Put the worker's steps in the order the code runs them.

  1. Generate the key
  2. Save the key with the job
  3. Send the charge with the key
  4. On timeout, resend with the same key

Saving before sending is the step that survives a crash between the two.
