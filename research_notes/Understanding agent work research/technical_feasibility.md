## 1. Agent surfaces: what each coding agent exposes before, during and after a change

### Takeaway
By late 2026 almost every major agent has a hook system with a "before tool call" event that receives the tool's arguments and can deny the call, so a third-party tool can see each individual edit before it lands and can block it. The agent's whole intended change is available before any edit only where a plan mode exposes the plan: Claude Code does this in a documented way (the `ExitPlanMode` hook payload carries the plan text and plan file path); for the others the plan is either a file in a home directory (Cursor), a stream item (Codex, from secondary sources) or not documented as interceptable.

### Cited Findings

- Transcripts: "stores transcripts as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`"; "The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release." - Headless: `claude -p` with `--output-format json|stream-json`, `--json-schema`, `--resume <session-id>`; without `--bare`, a `-p` session runs project hooks and MCP servers; `--bare` skips hooks entirely and "will become the default for `-p` in a future release." — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless) `[official documentation; yes]`
- Existing third-party proof that plan interception works: Plannotator's manual setup uses a `PermissionRequest` hook with matcher `ExitPlanMode`; "a hook holds `ExitPlanMode` open, and Claude waits until you decide"; "Send Feedback returns your annotations so Claude can revise it." — [Plannotator docs](https://docs.plannotator.ai/open-source/agents/claude-code) `[third-party tool documentation; sells AI tools: unknown, has an open-source edition]`

### Inferences
- Convergence: Claude Code, Codex, Copilot, Devin CLI, Gemini CLI, Cursor and Cline all have a pre-tool event with tool arguments and a deny path, and several read each other's config (Copilot CLI and Devin CLI read `.claude/settings.json`). One hook script with thin adapters is feasible for at least Claude Code, Codex, Copilot CLI and Devin CLI. Field names differ (snake_case, camelCase, `toolArgs` versus `tool_input`).
- Three realistic points to ask for a prediction before any edit: (a) at prompt submission (`UserPromptSubmit` / `beforeSubmitPrompt` / `BeforeAgent`), where the tool knows the request but not the agent's intent; (b) at plan approval, where the full intended change exists as text (documented only for Claude Code); (c) at the first write tool call, by denying or holding it, where only the first edit is known.
- A hook cannot itself show rich UI in a terminal agent. Plannotator's pattern (hook holds the call open, opens a browser page, returns the decision) is the working precedent. MCP Apps would put the UI in the conversation, but only in hosts that support the extension, and the terminal agents are not on the list I could confirm.
- After the change, everything needed for a mechanical check is available without the agent's cooperation: `Stop`/`agentStop` events fire, and `git diff` gives the actual change. Transcripts are readable but every vendor that documents them says the format is unstable.
- Fail-open defaults (Copilot timeouts, Cline `hookErrorMode: "ignore"`, Codex "not a complete enforcement boundary") mean a prediction gate built on hooks is a prompt, not an enforcement mechanism.

- Antigravity CLI (Gemini CLI's stated replacement), Amazon Q/Kiro, JetBrains Junie, OpenCode, Goose, Zed: not researched.

## 2. Computing a system-level picture of a repository mechanically

### Takeaway
A module-level dependency graph from imports is cheap, deterministic and works from source alone in the common languages; this is the reliable base layer. Function-level call graphs are available but lose a large share of real edges in dynamic languages (about 70% recall for the best Python tool measured), and the most precise indexes need a type checker or a build.

### Cited Findings
- dependency-cruiser "Validate and visualise dependencies. With your rules." for JavaScript, TypeScript, LiveScript, CoffeeScript (ES6, CommonJS, AMD); outputs include dot, json, html, csv, mermaid, text; default rules cover circular dependencies, orphans, and dependencies missing from package.json. — [dependency-cruiser README](https://github.com/sverweij/dependency-cruiser) `[repository README; no]`
- import-linter lets you "impose constraints on the imports between your Python modules"; contract types include forbidden, layers, independence, protected, acyclic siblings and custom. — [import-linter docs](https://import-linter.readthedocs.io/en/stable/) `[official documentation; no]`
- Python call graphs: PyCG reports "high rates of precision ~99.2%, and adequate recall ~69.9%" on micro- and macro-benchmarks, at "0.38 seconds for 1k LoC on average". — [Salis et al., PyCG, ICSE 2021](https://arxiv.org/abs/2103.00587) `[peer-reviewed study; no]`
- JavaScript call graphs: in a manual check of 348 edges, ACG had precision above 99% and TAJS about 98%; the union of all tools found all true edges but with combined precision "only slightly above 83%". The original ACG paper reported precision and recall "typically above 80%", and a later root-cause study found ACG recall drops under stricter metrics. — [Antal et al., Static JavaScript Call Graphs: a Comparative Study](https://arxiv.org/abs/2405.07206v1) and [root-cause study](https://arxiv.org/pdf/2205.06780), both via search summary `[peer-reviewed studies; no]`
- SCIP indexing speed: scip-typescript "ranging anywhere between 1k-5k lines of code per second" on a 2019 MacBook Pro; Sourcegraph's own CI indexing went from "~40 minutes (12 parallel jobs) down to ~5 minutes (1 job)". A user reported about 20 minutes for ~2M lines of TypeScript on an M1, with most time spent re-creating the type checker. — [Sourcegraph blog](https://sourcegraph.com/blog/announcing-scip-typescript) `[vendor engineering blog, via search summary; yes]`; [GitHub issue](https://github-redirect.dependabot.com/sourcegraph/scip-typescript/issues/175) `[user report, via search summary; no]`
- stack-graphs (name resolution without a build, on tree-sitter) is dead upstream: "This repository was archived by the owner on Sep 9, 2025"; "This repository is no longer supported or updated by GitHub." — [github/stack-graphs](https://github.com/github/stack-graphs) `[repository README; GitHub sells AI tools: yes]`
- CodeQL: "For most compiled languages, CodeQL needs to invoke the required build system to generate a database" (C/C++, C#, Go, Java/Kotlin, Rust, Swift); JavaScript/TypeScript, Python and Ruby need no build; "for C/C++, C#, Java and Rust, there is an option to generate a database without building the code." — [CodeQL CLI docs](https://docs.github.com/en/code-security/codeql-cli/getting-started-with-the-codeql-cli/preparing-your-code-for-codeql-analysis) `[official documentation; yes]`
- Build-graph tools give a ready-made system graph where a monorepo uses them. Nx (24+) "uses Git to find the files your branch changed" and selects each task whose declared inputs include a changed file; `nx affected -t build --explain` prints why tasks are affected; undeclared reads "can be missed". — [Nx affected docs](https://nx.dev/docs/features/ci-features/affected) `[official documentation; vendor sells developer tooling including AI features: yes]`
- Protobuf: `buf breaking` compares against a past version, including a git ref (`buf breaking --against '.git#branch=main'`), with rule categories FILE, PACKAGE, WIRE_JSON, WIRE; "Passing a stricter category implies passing every looser one." — [Buf breaking docs](https://buf.build/docs/breaking/) `[official documentation; no AI product found]`
- OpenAPI: oasdiff reports `breaking` ("changes that break existing API clients"), `changelog` and full `diff`, in html, json, markdown, text, yaml. — [oasdiff README](https://github.com/oasdiff/oasdiff) `[repository README; no]`
- Database migrations: Atlas lint analyzers flag destructive changes (DS101-DS103: drops of schemas, tables, columns; "result in loss of data"), data-dependent changes (MF101-MF104, e.g. adding a unique index or NOT NULL), backward-incompatible changes (BC101-BC104: renames and drops), and non-linear migration history. Several analyzers are Pro-only. — [Atlas lint analyzers](https://atlasgo.io/lint/analyzers) `[official documentation; vendor has paid tier, AI features unknown]`

### Inferences
- With only git and no build, a tool can get: file and directory structure, import edges (tree-sitter or language-specific parsers), package manifests and lockfile dependencies, schema files (OpenAPI, proto, SQL migrations), and git history. This is enough for a module graph and for interface and schema diffs. It is not enough for precise call resolution in typed compiled languages.
- For dynamic languages the choice is precision over recall: PyCG and ACG rarely invent edges but miss many. A diagram drawn from them will be sound in what it shows and silent about some real connections; the tool must say so.
- stack-graphs being archived removes the main build-free precise name-resolution option; SCIP indexers (which run the language's type checker) are the surviving precise route and cost minutes on large repos.

### Gaps
- Not researched this session (background, not verified; source before use): Joern code property graphs; Semgrep and ast-grep rule engines; Madge and pydeps; ArchUnit; Bazel `query`/`aquery`; GraphQL schema diff (graphql-inspector); `terraform plan -json` as a mechanical infrastructure diff; route-table extraction from web frameworks; LSIF; LSP as a query surface (call hierarchy, references); tree-sitter language coverage.
- No measured numbers found for import-graph precision and recall (missed dynamic imports, dependency injection, string-based routing, reflection). The import-linter page does not state its limits.
- No source found that measures a full "index a mid-sized repository" time for tree-sitter-only import graphs.
- Jelly (hybrid JavaScript call graph) recall figures: not found.
- CodeQL `build-mode none` accuracy loss: the page states none.

## 3. Computing the difference a change makes at the system level

### Takeaway
Diffing two mechanically built graphs (before and after) is straightforward and deterministic for modules, dependencies, cycles, API schemas and migrations. Predicting which other parts are affected is much weaker: call-graph impact prediction trades precision against recall, tree-diff tools mis-map a fifth or more of file revisions, and the best-performing selection methods at scale are statistical, not exact.

### Cited Findings
- Call-graph impact prediction, evaluated on 17,000 mutants across 10 Java projects with four call-graph types: "graph sophistication increases the completeness of impact prediction" but "the most basic call graph gives the best trade-off between precision and recall for impact prediction." (Abstract gives no numbers.) — [Musco, Monperrus, Preux, Software Quality Journal 2017](https://arxiv.org/abs/1812.06286) `[peer-reviewed study; no]`
- Co-change mining for impact prediction: a review reports Hassan et al.'s combination raising precision "up to 49%" while recall fell "down to 51%"; one association-rule study reported about 90% precision and recall on two Apache projects, with the review questioning the setup. — [search summary of a co-change review](https://dergipark.org.tr/download/article-file/747718) `[review article, via search summary; no]` Weak: numbers seen only in a search digest.
- AST differencing: a differential-testing study over 263,165 file revisions in ten Java projects found "GumTree, MTDiff and IJM generate inaccurate mappings for 20%-29%, 25%-36% and 21%-30% of the file revisions, respectively"; the detector's own precision was 0.98-1.00 and recall 0.65-0.75 against expert judgement, so true rates may be higher. — [Fan et al., ICSE 2021](https://arxiv.org/abs/2103.00141v1), via search summary `[peer-reviewed study; no]`
- difftastic: "Not all of these cases work well in difftastic yet" (delimiter changes, reordering, sliders, comments and strings); "Difftastic will fall back to a line-oriented diff if any parse errors occur". — [difftastic manual, tricky cases](https://difftastic.wilfred.me.uk/tricky_cases.html) `[official documentation; no]`
- Test impact analysis works from a recorded map of which source each test executes: "Code coverage or instrumentation, while tests are running is the mechanism by which that intelligence is gleaned." Caveats named: non-code inputs ("the tool cannot automatically determine which tests depend on a given resource file"), new tests not yet instrumented, and inconsistent savings. — [Hammant, The Rise of Test Impact Analysis, martinfowler.com, Aug 2017](https://martinfowler.com/articles/rise-test-impact-analysis.html) `[practitioner article; opinion with examples; no]`
- Predictive test selection at Facebook (machine-learned, not exact): "over 95% of individual test failures" and "over 99.9% of faulty changes are still reported back to developers" while it "reduces the total infrastructure cost of testing code changes by a factor of two." — [Machalica et al., 2018](https://arxiv.org/abs/1810.05286) `[industry study; Meta sells AI tools: yes]`
- Build-graph "affected" sets: Nx notes that selection "can still be large" when widely depended-on projects change, and that `dependsOn` alone does not make a task affected. — [Nx affected docs](https://nx.dev/docs/features/ci-features/affected) `[official documentation; yes]`

### Inferences
- "Architecture diff" needs no research-grade technique: build the module graph at the base commit and at the head commit, then set-difference nodes and edges, and run cycle detection on each. Its error is exactly the error of the underlying import graph.
- The reverse-dependency closure of changed modules ("what depends on what changed") is computable but over-approximates actual impact; the Musco result says more sophisticated graphs raise completeness at the cost of precision. It should be presented as "could be affected", not "is affected".
- Behaviour-level differences (which tests fail on old versus new code) are the most trustworthy signal but need a runnable test suite, which a tool with only git does not have. The agent itself often does run tests, and hooks see those commands and results (`PostToolUse` carries `tool_response`).

### Gaps
- Not researched this session (background, not verified): differential testing tools, snapshot testing, OpenTelemetry trace comparison, coverage diffs, taint analysis for change impact, GitHub Semantic (status unknown).
- No recent (2020 onward) survey of change impact analysis with pooled precision/recall was read. The Musco paper's numeric results were not seen (abstract only).
- No source found for an off-the-shelf tool that outputs a module-graph diff between two commits (dependency-cruiser's README does not mention one). Whether one exists is unknown from this session.
- No study found measuring how well a module-level diff predicts reviewer-relevant impact.

## 4. Checking a prediction: what can be scored by a mechanical fact

### Takeaway
Predictions phrased as closed choices over computed objects (which modules are touched, whether a new dependency edge or cycle appears, whether a public API schema or protobuf breaks, whether a migration is destructive) can be scored without a model, each with a known error source. Predictions about behaviour or about "what else is affected" can only be scored approximately, and free-text predictions need a model to map text onto those facts.

### Cited Findings
- Files and edits actually made are exact: Claude Code `PreToolUse`/`PostToolUse` carry `file_path` and edit strings; Cursor `afterFileEdit` carries `file_path` and `edits`; Cursor `subagentStop` carries `modified_files`. — [Claude Code hooks](https://code.claude.com/docs/en/hooks), [Cursor hooks](https://cursor.com/docs/agent/hooks) `[official documentation; yes]`
- The plan text is available for comparison in Claude Code (`tool_input.plan` on `ExitPlanMode`). — [Claude Code hooks](https://code.claude.com/docs/en/hooks) `[official documentation; yes]`
- Protobuf compatibility is a mechanical verdict with graded strictness (FILE implies PACKAGE implies WIRE_JSON implies WIRE). — [Buf](https://buf.build/docs/breaking/) `[official documentation; no]`
- OpenAPI breaking changes are a mechanical verdict from oasdiff's rule set. — [oasdiff](https://github.com/oasdiff/oasdiff) `[repository README; no]`
- Migration risk classes are mechanical in Atlas: destructive, data-dependent ("may succeed or fail, depending on the data that is stored in the database"), backward-incompatible. The analyzers page has no reversibility analyzer; it says dropped data is deleted "with no way to recover it". — [Atlas analyzers](https://atlasgo.io/lint/analyzers) `[official documentation; see above]`
- "Which modules depend on what changed" inherits call-graph and import-graph limits: about 70% recall for Python calls (PyCG); simplest call graph gives the best precision/recall trade-off for impact (Musco et al.). — [PyCG](https://arxiv.org/abs/2103.00587); [Musco et al.](https://arxiv.org/abs/1812.06286) `[studies; no]`
- A model can be used inside the hook itself: Claude Code has `prompt` hooks (single-turn model evaluation) and Devin hooks can be "a shell command or an LLM prompt". — [Claude Code hooks](https://code.claude.com/docs/en/hooks); [Devin Desktop hooks](https://docs.devin.ai/desktop/cascade/hooks) `[official documentation; yes]`

### Inferences
Scoring table (my synthesis from the findings above; error notes are reasoned, not measured, unless a source is named):

| Prediction | Mechanical fact that scores it | Main error source |
|---|---|---|
| Which files or modules will change | `git diff --name-only` mapped to modules | None for files; module mapping depends on the chosen grouping |
| Will a new dependency between modules appear; will a cycle appear | Import-graph diff before/after | Dynamic imports, DI, reflection missed (no measured rate found) |
| Will a new third-party dependency be added | Manifest and lockfile diff | Essentially exact |
| Will a public HTTP or RPC interface change, and break clients | oasdiff / buf breaking on schema files | Only if a schema file exists and is kept in sync with code |
| Will the database schema change; is it destructive | Migration file diff plus Atlas-style lint | Data-dependent cases cannot be decided without the data; reversibility not directly analysed |
| Which other modules could be affected | Reverse-dependency closure | Over-approximates; under-approximates where edges are missed (PyCG ~70% recall for calls) |
| Which tests will fail | Run tests on old and new code | Needs a runnable environment; flaky tests |
| "This is a small/contained change", "this touches the payment flow" | No single fact | Needs a model, or must be rephrased as a closed choice |

- The practical design consequence: ask for the prediction as a selection on the computed "before" diagram (click the modules you expect to change; tick expected new edges or interface changes). Then scoring is set comparison and no model is needed. Free text can be collected in addition but scored separately and labelled as model-judged.
- Because the "after" facts are computed by the same pipeline as the "before" picture, systematic blind spots (missed edges) cancel in the comparison but remain invisible to the developer; the tool should state what the graph cannot see.

### Gaps
- No study found that measures the error rate of a language model mapping a developer's free-text prediction onto a set of modules or edges.
- No mechanical test for migration reversibility was found in the page read (Atlas down-migration page not fetched).
- No source found on scoring partial matches (e.g. predicted 3 modules, actual 5) in a way validated against learning outcomes; that is outside this technical scope.

## 5. Drawing: automatic layout and limits at repository scale

### Takeaway
Layout engines are available and free, but evidence says node-link diagrams stop being readable quickly: one controlled study found matrices beat node-link diagrams on most tasks beyond about twenty nodes. A repository diagram therefore has to be aggregated to a few dozen boxes at most, and tools impose their own hard caps.

### Cited Findings
- Ghoniem, Fekete and Castagliola (InfoVis 2004) compared node-link and matrix views on seven tasks with random graphs of 20, 50 and 100 nodes: "When graphs are bigger than twenty vertices, the matrix-based visualization performs better than node-link diagrams on most tasks. Only path finding is consistently in favor of node-link diagrams". — [bibliographic record with abstract, via search summary](https://bibbase.org/network/publication/ghoniem-fekete-castagliola-acomparisonofthereadabilityofgraphsusingnodelinkandmatrixbasedrepresentations-2004) `[peer-reviewed study; no]`
- A later replication with a larger sample found the node-link advantage "attenuated in the larger (50-node) network"; Okoe, Jianu and Kobourov revisited the comparison on a real 258-node, 1090-edge graph. — [search summary](https://par.nsf.gov/servlets/purl/10146467) `[peer-reviewed studies; no]`
- Mermaid has hard limits by default: `maxEdges` default `500` ("Defines the maximum number of edges that can be drawn in a graph") and `maxTextSize` default `50000`. A `layout` property selects the layout algorithm. — [Mermaid config schema](https://mermaid.js.org/config/schema-docs/config.html) `[official documentation; Mermaid has a commercial arm with AI features: yes]` Note: the fetch reported the `layout` default as `"elk"`; I could not confirm that against the rest of the page (only the first 100k of 440k characters were read) and it conflicts with my background understanding that dagre is the default. Treat as unverified.
- dependency-cruiser emits dot (rendered with Graphviz) and mermaid directly. — [dependency-cruiser README](https://github.com/sverweij/dependency-cruiser) `[repository README; no]`
- LLM-generated architecture views fail on level of detail: across 340 repositories and 4,137 generated views, models "consistently exhibit granularity mismatches, operating at the code level rather than architectural abstractions." — [Sathvika, Dhar, Vaidhyanathan, arXiv 2603.21178, March 2026](https://arxiv.org/html/2603.21178v1) `[preprint study; no]`

### Inferences
- Choosing the level of detail is the hard part, not layout. A mechanical default that needs no model: collapse the import graph to top-level directories or declared packages (workspace packages, Python top-level packages, Go modules), show only the changed modules plus their one-hop neighbours, and collapse the rest.
- For a change-focused diagram the node count is naturally small (changed modules plus neighbours), which keeps it under the roughly-twenty-node range where node-link diagrams did well in the Ghoniem study. A whole-repository view should fall back to a dependency matrix or a collapsed cluster view.
- Path-following ("what depends on this, transitively") is the one task where node-link stayed better in that study, and it is the task this tool cares about; that supports node-link for the focused view.

### Gaps
- Not researched this session (background, not verified): ELK layered algorithm options, Dagre maintenance status, D2 (TALA is a paid layout engine), Graphviz dot scaling, C4 model levels (context, container, component, code), Structurizr, Purchase's edge-crossing studies, hierarchical edge bundling.
- No study found on readability of architecture diagrams specifically for developers reviewing a change.
- No evidence found on which automatic clustering of modules (directory-based versus algorithmic architecture recovery) developers find recognisable.

## 6. Using a language model to infer components, name them and summarise a change

### Takeaway
Current evidence says models alone are not reliable for recovering architecture: the best measured agent reached a mean F1 of about 0.6 on microservice systems, and generated views are mostly judged incomplete. Reported errors lean towards omission and wrong level of detail more than invented edges, and every study that grounds the model in computed dependency facts reports improvement.

### Cited Findings
- Liljas, Esposito, Lenarduzzi, Taibi (ESEM 2026, published 5 Oct 2026): a single tool-using agent on 17 open-source Java microservice applications, 20 runs each, inferring services, connections and endpoints. "GPT-4o achieved a mean F1 score of 0.604"; Llama4 "F1 = 0.254". Both had higher precision than recall, read as a tendency to "under-represent architectural relationships rather than hallucinate them." Service-to-service connections were hardest. Conclusion: "current capabilities remain insufficient for fully reliable reverse engineering." (Abstract only.) — [LIPIcs ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.62) `[peer-reviewed study; no]`
- Sathvika et al. (arXiv, 22 Mar 2026): 340 repositories, 13 configurations, 4,137 views; DeepSeek-V2.5, Claude 3.5 Sonnet, GPT-4o with zero/one/few-shot prompts, Claude Code as a general agent, and a custom multi-agent "ArchView". Results: "Completeness failures exceeded 82% for most zero-shot models"; Claude Code had "a 71.8% clarity failure rate and 90.2% consistency failures"; ArchView had the best clarity (22.6% failure) and 50.0% "Meets" for level of detail in human evaluation; few-shot "reduces clarity failures by 9.2% compared to zero-shot baselines." Scoring used an LLM judge plus 110 human evaluations. The paper does not analyse hallucination explicitly. Models tested are older than those current in Nov 2026. — [arXiv 2603.21178](https://arxiv.org/html/2603.21178v1) `[preprint study; no]`
- Grounding helps: an ASE 2025 study grounds prompts in static-analysis facts, detects hallucinations and repairs them, reporting "11% accuracy improvement over state-of-the-art methods"; ArchAgent (arXiv, Jan 2026) found in ablation that "dependency context improves the accuracy of generated architectures"; SemRef (ICSE 2026) uses LLMs with dependency analysis to refine outputs of existing recovery tools on 9 projects with ground truth. — [search summary: ASE 2025 paper](https://tsingpig.github.io/files/ASE%202025%20papers/ASE%202025/pdfs/ASE2025-5DQL9ko9OwpjaORDC0qal7/573300a355/573300a355.pdf), [ArchAgent](https://arxiv.org/pdf/2601.13007), [SemRef](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/72/Semantic-Enhanced-Automatic-Refinement-of-Architecture-Recovery-Results-Using-LLMs) `[studies, seen via search summary only; no]`
- Code2UML (2026) states that passing a whole codebase representation to a single model call results "in truncated outputs, hallucinated relationships", and proposes deterministic context compaction plus specialised agents. — [arXiv 2605.24453, via search summary](https://arxiv.org/pdf/2605.24453) `[preprint; no]`
- Auto-DSM evaluation (2026) defines hallucination as the model "generating confident dependencies that are unsupported or incorrect" and reports "systematic hallucination and abstention failures". — [alphaxiv 2607.05985, via search summary](https://www.alphaxiv.org/abs/2607.05985) `[preprint; no]`

### Inferences
- The safe division of labour: edges and nodes come only from computed facts; the model is allowed to group, name and describe them, and any edge the model mentions that is not in the computed graph is dropped or flagged. This removes invented edges by construction and leaves only naming and grouping errors.
- Because measured failure is mainly omission and wrong granularity, a model-chosen grouping should be checked mechanically for coverage (every file belongs to exactly one component) rather than trusted.
- Summaries of a change can be grounded the same way: give the model the computed graph diff and schema diffs, and require each sentence to cite a computed item.

### Gaps
- No per-edge hallucination rate for model-generated dependency diagrams was read (the ESEM paper's full text and the Auto-DSM numbers were not fetched).
- No evaluation found using the frontier models of late 2026; the two quantitative studies used GPT-4o, Claude 3.5 Sonnet, DeepSeek and Llama variants.
- No study found on accuracy of model-written natural-language summaries of a diff at the system level, or on the accuracy of model-chosen component names.
- ECSA 2025 study on off-the-shelf LLMs for architecture recovery: findings not retrieved.

## 7. Performance and practicality

### Takeaway
Parsing-based import graphs and schema diffs are fast enough to run inside a hook; type-checker-based indexes take minutes on large repositories and belong in a background step. Hook time budgets are generous on paper (600 s defaults) but several agents fail open on timeout, so the before-step must be quick or asynchronous.

### Cited Findings
- PyCG: "0.38 seconds for 1k LoC on average". — [PyCG](https://arxiv.org/abs/2103.00587) `[study; no]`
- scip-typescript: 1k-5k lines per second (vendor figure); ~20 minutes for ~2M lines (one user report). scip-clang on a 2.75M-line project on an 88-core machine took "about 30%-50% more time than a baseline of type-checking all translation units in parallel." — [Sourcegraph blog and issue, via search summary](https://sourcegraph.com/blog/announcing-scip-typescript) `[vendor blog and user report; yes]`
- Hook time limits: Claude Code command, http and mcp_tool hooks default to 600 s; prompt hooks 30 s; `SessionEnd` hooks share 1.5 s. Codex command hooks default to 600 s. Plannotator sets its plan-review hook timeout to 345600 (seconds, i.e. four days) to wait for a human. — [Claude Code hooks](https://code.claude.com/docs/en/hooks); [Codex hooks](https://learn.chatgpt.com/docs/hooks); [Plannotator](https://docs.plannotator.ai/open-source/agents/claude-code) `[official documentation; see above]`
- Fail-open behaviour: Copilot "Command hook timeouts are always fail-open"; Cline default `hookErrorMode` `"ignore"`. — [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-configuration); [Cline SDK plugins](https://docs.cline.bot/sdk/plugins.md) `[official documentation; yes]`
- Language coverage is uneven: dependency-cruiser covers the JavaScript family only; import-linter Python only; CodeQL needs a build for Go, Swift and Kotlin and has a no-build option for C/C++, C#, Java, Rust. — [dependency-cruiser](https://github.com/sverweij/dependency-cruiser); [import-linter](https://import-linter.readthedocs.io/en/stable/); [CodeQL](https://docs.github.com/en/code-security/codeql-cli/getting-started-with-the-codeql-cli/preparing-your-code-for-codeql-analysis) `[documentation; see above]`
- Headless runs may skip the tool entirely: Claude Code `--bare` skips hooks, and the docs say it "will become the default for `-p` in a future release." — [Claude Code headless](https://code.claude.com/docs/en/headless) `[official documentation; yes]`
- Cloud agents constrain a third-party tool: Copilot cloud agent reads hooks only from `.github/hooks/*.json`, runs them in an ephemeral sandbox, and blocks outbound hosts by default; Devin `SessionEnd` is "not fired in cloud sessions". — [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-configuration); [Devin CLI hooks](https://docs.devin.ai/cli/extensibility/hooks/overview) `[official documentation; yes]`

### Inferences
- What is not possible today, as far as this session's evidence goes:
  - Knowing the agent's complete intended change before any edit, in a documented way, outside Claude Code plan mode. Elsewhere the tool sees the user's prompt, then individual tool calls one at a time.
  - Forcing a prediction step in cloud or headless runs with no human present; hooks can block, but there is nobody to answer.
  - A complete, precise call graph for Python or JavaScript without running the code.
  - A single maintained, build-free, cross-language precise name-resolution library (stack-graphs is archived).
  - Trusting a model alone to draw the system diagram.
- What is practical: a per-language import-graph extractor behind a common graph format, computed at session start (cached per commit) and again at `Stop`; diff the two; draw only the neighbourhood of the change.
- Incremental update is natural because both snapshots are keyed by git commit plus dirty files; only changed files need re-parsing for an import graph.

### Gaps
- No measured end-to-end timing found for building a tree-sitter import graph of a mid-sized repository (for example 100k-500k lines); the figures above are for type-aware indexers and one Python call-graph tool.
- Incremental indexing support in SCIP indexers: not researched.
- scip-python timings: the Sourcegraph post reportedly has a table; not retrieved.
- How each agent behaves when a hook blocks for a long time waiting for a human (UI state, timeouts on the model side) beyond Plannotator's Claude Code example: unknown.
- Whether hook payload schemas are stable across versions: Claude Code and Codex both warn only about transcripts; no stability promise for hook payloads was seen for any agent.
